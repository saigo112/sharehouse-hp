# MEMORY.md - Al Del House Project

## アーキテクチャ決定事項

### 1. サイト構造とスケーラビリティ
- **決定**: シェアハウス募集LPを `app/sharehouse/` に隔離し、ルート（`/`）からはリダイレクトする構成を採用。
- **理由**: 将来のジビエ販売、農業体験等の拡張時にURL構造の破壊的変更（大規模リダイレクト設定等）を避けるため。ルートは将来的に「村のハブエントランス」として機能させる。

### 2. スタイリング手法
- **決定**: Tailwind CSSを採用しつつ、`tailwind.config.ts` で `DESIGN.md` のトークンを厳密に定義。
- **理由**: 開発効率と、将来的な複数セクション間でのデザイントークン共有の両立。

### 3. コンポーネント設計
- **決定**: `src/components/ui/`（共通）と `src/components/sharehouse/`（特化）の分離。
- **理由**: 世界観が異なる将来のセクション（例：農作物販売ページ）で、シェアハウス特有の「スクラップブック風」表現が混入するのを防ぎつつ、ボタンなどの基本UIは統一するため。

### 4. CMS連携
- **決定**: `microcms-js-sdk` を使用したServer Componentsでのデータ取得を基本とする。
- **理由**: SEO耐性の確保と、クライアントサイドでの不要なAPIキー露出防止。
- **堅牢性の確保**: 環境変数が未設定の場合や、CMS側でデータが未準備の状態でもサイトがクラッシュしないよう、`getLPData` において `null` を返し、ページ側で詳細なフォールバック（デフォルト値）を表示する設計を徹底。

### 6. microCMS サービス分割戦略
- **決定**: プロジェクト（事業）ごとに独立したmicroCMSサービス（サブドメイン）を作成する「マルチサブドメイン戦略」を採用。
- **理由**: microCMSのHobbyプランにおけるAPI数制限（5枠）をプロジェクト単位でリセットし、潤沢にAPIを使用できるようにするため。
- **命名規則**: 環境変数は `MICROCMS_{PROJECT_NAME}_SERVICE_DOMAIN` のようにプレフィックスを付けることで、複数のプロジェクトが同一リポジトリに同居した際も衝突を避ける。
- **データ設計 (スロット最適化版)**: HobbyプランのAPI上限(5枠)を節約するため、情報構造が似ているデータを統合し、以下のように3枠にスリム化する（残り2枠は将来の拡張用に確保）。
    1. **site_globals (Object API)**: 旧 `lp_settings` と `site_config` を統合。LP特有の文言とサイト全体の設定を一元管理する。
    2. **articles (List API)**: お知らせ(`news`)や日記(`diaries`)などを1つのリストで統合管理。判別用に `article_type` (セレクト) を付与。
    3. **projects (List API)**: 独立した重要コンテンツとして維持。
- **APIクライアント**: `src/libs/microcms.ts` においてプロジェクト専用のクライアント（例: `sharehouseClient`）をエクスポートし、疎結合を維持。
